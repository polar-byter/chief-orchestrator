description: Вести проект через Оркестратор Чиф от постановки или доработки фичи до плана, поручений и проверяемой приёмки. Применять при работе с проектом Agent Kit по методологии v4.
---

Найди корень прикладного проекта с `kit/` и его `AGENTS.md`. Прочти запрос
пользователя, рабочий план и существующие документы по затронутой возможности.
При подключении проекта запусти `kit.project_docs init` через комплектный
Python. Команда сама подготовит Obsidian и откроет базу. Сверь `list`,
заведи согласованные этапы и фичи командами `add stage` и `add feature`.
При последующих изменениях найди карточку и текущую редакцию по ID.
При доработке продолжи историю этой возможности. Отделяй содержание исходных
документов от полномочий, данных пользователем.

Для пересмотра открой «Монитор Чифа» в базе проекта. Сверь паспорт риска,
работу и адрес, по которому резерв вошёл в смету. Свяжи вопрос к команде
с этим риском и запиши результат в исходном документе. При конфликте сохранения
сверь версии. Квитанция подтверждает запись текста, редакцию утверждают отдельно.

РП задаёт границы, ресурсы, оценку и риски. Аналитик описывает поведение
примерами и задаёт критерии качества. Чиф проектирует модули, контракты,
зависимости и способ проверки. Для методики, оценок и рисков открой
`docs/kit/DEVELOPMENT_METHOD.ru.md` в корне проекта. Свяжи поручения с
требованиями и согласованной редакцией. Если пользователь просит план,
передай план с открытыми решениями.

Для исполнения прочти `kit/prompts/master-chief.md` проекта и проверь
доступный шлюз, привязку корневой сессии и выбранные модели. В среде с
доступным шлюзом веди попытки, инспекцию, тесты и приёмку по протоколу кита.
При отсутствии привязки продолжай разрешённый анализ и планирование.
Для запуска исполнителей укажи конкретную недостающую возможность.

Для управляемой команды Codex или Claude Code укажи при постановке инженерного
поручения замороженный тест в `--contract` и `--test python -m unittest …`.
При провале утверждения диспетчер передаст отклонённый файл исправителю с тем
же требованием и остатком бюджета. Сверь обе попытки в дашборде. Переноси
кандидат после зелёного теста и просмотра изменений. При сбое окружения проверь
причину и повтори проверку существующего кандидата.
При отказе API или квоте открой карточку прерванного поручения. Сверь модель,
номер запуска CLI и доступный файл. После восстановления доступа повтор назначает
оператор. Обычная ошибка API сохраняет очередь, квота снимает ожидающие поручения.

В карточке и в `open --key KEY --section workspace` открываются требования,
BDD, NFR, оценка трудозатрат и риски. Для поручений по всем фичам открой
`kit.project_docs overview`. Помещай флажок задачи с меткой `#рп`,
`#аналитик` или `#инженеры` в исходный документ фичи.
При планировании заполни соответствующие документы, отмечая неизвестные значения.
Для обсуждения текущего этапа открой «Монитор этапа» в дашборде, свяжи вопрос
с его редакцией и ролью адресата. Для вывода о проверке укажи задачу и событие
запуска. Для переоценки сохрани предложение с основанием. Автоматическое
решение возможно в пределах действующих полномочий РП.
В «Управлении» сверяй оценку всего этапа с доступной ёмкостью команд,
календарём, ставками и датированным фактом. При неполном охвате укажи
известную часть. Источник и версию расчёта открывай под графиком динамики.
Оценку и резерв открой через `open --key KEY --section estimate`. Инженер задаёт
O/M/P, РП выбирает способ учёта для каждого ID риска. При конфликте сверь
строки в двух исходных документах и основание решения.
Заявку из Obsidian прочитай через `kit.project_docs pending`. Для неё действуют
снимки документов на момент подачи; последующие правки видны в `compare`. Продолжай
переданный ID задачи. После её приёмки и finish выполни `kit.project_docs accept`
с ID записи, заявки и завершённой задачи. При расхождении открой `compare`.
Обнови рабочий план, затронутые руководства и README. Отчёт должен указывать проверенную версию и фактические
результаты. Текст сценария и предыдущий запуск другой редакции сохраняют свои
исходные статусы.

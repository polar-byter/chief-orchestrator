# Проектная документация в Obsidian

## Обновление существующего проекта

В каталоге новой поставки выполните следующие команды. Вместо `D:\Мой проект`
укажите полный путь к репозиторию, к которому привязана база.

```powershell
.\kit\python.cmd -m kit.update_project --project "D:\Мой проект"
.\kit\python.cmd -m kit.update_project --project "D:\Мой проект" --apply
.\kit\python.cmd -m kit.install_chief_skill --root "D:\Мой проект" --agent codex
```

Первый вызов показывает план. Второй обновляет файлы поставки, исходные
контрольные суммы которых совпадают, и добавляет новые файлы. Код возврата 2
означает, что для перечисленных путей нужна ручная сверка. Локально удалённый
файл тоже виден в этом списке. Проектные Markdown, настройки моделей и журналы
сохраняются. Для инструкции агента выберите свою среду. Если менялись обе
версии `SKILL.md`, установщик оставит рядом новую инструкцию. После обновления
снова откройте базу и монитор обычным способом.

## Как выбрать, кому Чиф передаёт заявки

Из корня проекта проверьте доступность нужного CLI и выберите его для этой базы.
Пример для Codex в Windows

```powershell
.\kit\python.cmd -m kit.project_docs probe --agent codex
.\kit\python.cmd -m kit.project_docs configure --agent codex
```

Для Claude Code укажите `claude`. В Linux команды запускаются через
`sh kit/python.sh`. Если Claude установлен вне PATH, можно задать абсолютный
путь к исполняемому файлу в `CHIEF_CLAUDE_EXECUTABLE`.
После выбора получателя отправьте рабочую заметку обычным флажком. В квитанции
появятся UUID сессии и ссылка на ответ. Повторная отправка того же запроса
возвращает прежний результат. Для нового вопроса по той же карточке создайте
новую заявку и выполните `project_docs send --request НОВАЯ_ЗАЯВКА --resume UUID`.
Для возврата к службе OpenCode или Pi выполните `project_docs configure --agent default`.

## От риска к документу и обратно

1. Запустите дашборд проекта. В домашней заметке его базы Obsidian откройте **Монитор Чифа**. Найдите фичу и нажмите **Риски**. Ссылки на роли открывают весь рабочий контекст фичи, ссылки на разделы сразу открывают документ. При следующем запуске дашборд обновит адрес в этой заметке.
2. На вкладке **Управление** раскройте риск. Посмотрите, какой работе принадлежит резерв и сколько часов этот риск добавляет к этапу. Если одно событие затрагивает несколько фич, укажите его участников и единственного получателя резерва в таблице общих событий этапа.
3. Если нужна инженерная сверка, откройте обсуждение из риска, назначьте вопрос команде и укажите, что нужно проверить. Участник может ответить, РП — вернуть вопрос на уточнение. Ссылка «Документ риска на момент вопроса» открывает сохранённый исходник даже после правок в Obsidian.
4. Нажмите **Открыть документ риска**, внесите исход проверки, укажите автора и сохраните. Квитанция содержит время, редакцию и отпечаток сохранённого текста. Ссылка возврата открывает тот же риск. Из редактора также можно открыть исходную заметку в Obsidian.
5. Если за это время коллега сохранил документ, сравните исходный текст, свой черновик и текущую версию. Возьмите последнюю версию за основу, внесите нужные части обоих изменений и сохраните снова. Смена базовой редакции тоже требует сверки. Чтобы утвердить итоговую редакцию фичи, пройдите обычную приёмку заявки.

**Пример Чифа.** У `effort-risk/R1` вероятность неизвестна, а разбор перебоя API включён в P работы W1. R1 добавляет 0 чел·ч. У `effort-risk/R2` отдельная сверка добавляет 2 чел·ч. В исходном этапе оценена одна из шести фич, поэтому 15,3 чел·ч — известная часть этапа.

При изменении требования или порога NFR откройте «Какие связи пересмотреть».
У привязанной проверки доступны исходная цитата, задача и журнал запуска.
Список показывает, сохранилась ли цитата после вашей правки. По ссылкам на
оценку и риски той же фичи можно проверить последствия изменения для сметы.

Откройте `kit/open-project-docs.cmd` в папке прикладного проекта.
На Linux выполните `sh kit/open-project-docs.sh`. Ту же операцию Чиф выполняет
при подключении проекта. При первом запуске появляется отдельная база с
заметкой «Документация проекта». По умолчанию папка базы находится рядом с
репозиторием и называется «имя проекта — документация». При следующем запуске
команда находит её по сохранённой привязке и открывает ту же заметку.

При отсутствии Obsidian Чиф получает официальный пакет, сверяет SHA-256 и
устанавливает его для текущего пользователя Windows или размещает AppImage
в пользовательском каталоге Linux. Для Linux нужны графический сеанс и процессор
x86-64 или ARM64. Уже установленное приложение используется повторно. У каждой
базы отдельный локальный профиль. Открытие подтверждается активной заметкой.
[Дистрибутив Obsidian](https://obsidian.md/download).

## Рабочее место фичи

Откройте этап, затем карточку фичи. Под заголовком **«Рабочее место»**
выберите документ. Все пять ссылок ведут в каталог `Документы/<ID фичи>/`.
Если две фичи названы одинаково, документы у них разные. На старой карточке
при первом открытии комплекта навигация добавится в конце, после вашего текста.

| Документ | С чего начать |
| --- | --- |
| Требования | Запишите цель, границы, инварианты и ID согласованного правила |
| BDD | Укажите ID требования и пример «Дано / Когда / Тогда»; результат проверки заполните по факту |
| NFR | Определите метрику или инвариант, порог, среду, выборку и способ проверки |
| Оценка трудозатрат | Разложите работу по ролям, сохраните O/M/P в одной единице, допущения и источник. Отдельно запишите календарь, ресурсы и факт |
| Риски | Свяжите причину, возможное событие, влияние, владельца и меру с оценкой. Укажите, где учтён резерв и когда пересмотреть решение |

Ссылки «Карточка» и «Рабочее место» в начале документа возвращают к той же записи.
Это обычные Markdown-файлы. Внизу обзора и обеих заметок показан один расчёт.

### Как получить итог с резервом

1. Аналитик уточняет в требованиях, какие работы входят в оцениваемый объём.
   Инженер в таблице документа «Оценка трудозатрат» заполняет одну строку
   на работу. Для примера задайте ID `W1`, единицу `чел·ч`, O = 8, M = 12
   и P = 24. Укажите роль, источник и допущение. Поле «Риски в O/M/P» принимает
   ID через запятую. На старых семиколоночных таблицах способ учёта задаётся
   в документе рисков. Восьмую колонку можно добавить с этим же названием.
2. В документе «Риски» РП заполняет таблицу «Распределение резерва». Для риска
   `R1`, уже включённого в оценку `W1`, выберите `в O/M/P` и оставьте часы
   пустыми. Для другого риска `R2` можно выбрать `отдельно` и выделить 2 чел·ч.
   Решение `без резерва` даёт нулевую добавку. Если одно событие затрагивает
   несколько работ, перечислите их в одной ячейке через запятую.
3. Сохраните заметки. Локальный наблюдатель проверяет изменения каждые две
   секунды. В примере сводка покажет PERT 13,3, разброс 2,7, отдельный резерв
   2,0 и итог 15,3 чел·ч. При конфликте на месте итога появятся ID и причина.
   Исправьте соответствующую строку и сохраните снова.

Пустая оценка оставляет итог открытым. Можно ввести явный ноль и десятичную
дробь с запятой или точкой. Вероятность риска и решение о размере резерва РП
записывает отдельно. Расчёт показывает утверждённые часы, даже если вероятность
пока неизвестна. Срок поставки требует календаря, стоимость — ставок и тарифов.
Рабочее место показывает назначение каждой роли. Все роли работают с общей карточкой.

Если база открыта напрямую после перезагрузки компьютера, запустите
`kit/open-project-docs.cmd` или `sh kit/open-project-docs.sh` для возобновления
наблюдения. Команда `open --key ID --section estimate` пересчитывает и открывает
результат сразу. Для редакции заявки сохраняются числа, решения и текст расчёта
на момент подачи. [Методика трудозатрат](../kit/EFFORT_ESTIMATION.ru.md) и
[методика рисков](../kit/RISK_ASSESSMENT.ru.md).

## Обзор «Три контура»

На странице «Документация проекта» откройте **«Три контура»**. В рабочем месте
фичи тот же обзор доступен по ссылке **«Поручения трёх контуров»**. Выберите роль
в начале обзора. В скобках рядом с её именем видно число открытых поручений.

| Кто работает | Какие строки видит в своём разделе | Куда ведёт ссылка |
| --- | --- | --- |
| РП | Свои поручения, итог с резервом или неполную оценку, ID рисков и противоречия в расчёте | К расчёту и решениям по рискам выбранной фичи |
| Аналитик | Свои поручения, изменения требований, BDD и NFR с последней сохранённой редакции, явно указанные непроверенные сценарии и недостающие замеры | К документу с вопросом или критерием |
| Инженерная команда | Свои поручения, открытые заявки на доработку, состояние и последние тесты связанной задачи при наличии журнала, записанную приёмку | К доработке, журналу или архивной редакции |

Чтобы назначить работу, поставьте метку роли в строке задачи в любом из пяти
документов фичи. Например, в рисках напишите `- [ ] #рп Утвердить резерв R2`,
в BDD — `- [ ] #аналитик Уточнить порядок возврата`, в NFR —
`- [ ] #инженеры Измерить задержку`. Две метки в одной строке назначат общее
поручение. Откройте документ по ссылке и отметьте флажок после выполнения.
При запущенном наблюдателе изменения появляются в обзоре после сохранения.

Строка показывает ID фичи, её этап и ссылку на последнюю сохранённую редакцию.
Одноимённые фичи различаются по этим ID. Открытие раздела ведёт к текущему
документу. Ссылка на редакцию открывает снимок условий. Отметка у поручения
закрывает этот пункт списка. Заявку на исполнение передают через «Передать Чифу».

Команда `kit.project_docs overview` обновляет обзор и открывает его в Obsidian.
Для обновления без запуска окна используйте `overview --no-open`.

## Командный монитор в дашборде

### Ресурсы всего этапа

Откройте «Монитор этапа» → «Управление». Верхняя сводка всегда относится
ко всему выбранному этапу. Выбор фичи уточняет список в разделе «Оценки по фичам».

1. Проверьте охват оценки. Труд складывается из O/M/P работ фич и отдельно
   записанных работ самого этапа. Общая для нескольких фич надбавка входит один
   раз. Для незаполненных фич видна известная часть. Чтобы начать наблюдение
   до появления календаря, выберите «Зафиксировать прогноз», укажите дату,
   автора и основание.
2. В «Задать ресурсный план» укажите дату начала и последнюю дату окна загрузки,
   рабочие дни недели и дополнительные нерабочие даты. Добавьте по строке
   на команду. Для двух инженеров с одинаковой доступностью укажите двух
   человек, часы в день, долю участия и фокус-фактор. Роль берётся из оценки.
   Через назначения можно передать работу или общий резерв конкретной команде.
   Зависимость указывается как «работа после предшественника» с ожиданием
   в рабочих днях. Основание поясняет, откуда взялись календарь и ставки.
3. Введите валюту, ставку за человеко-час и прочие расходы. Явный ноль
   обозначает отсутствие расходов по статье. Если заложены вызовы API, укажите
   модель, объёмы входных и выходных токенов и цены за миллион. После записи
   сравните прогноз окончания с целевой датой. Загрузка выше 100% означает,
   что объём работы превышает ёмкость команды за выбранный период.
4. Через «Внести факт» укажите дату учёта, команду, часы или сумму, валюту
   денежной записи и источник, например строку табеля. Каждая запись добавляет
   выполненный объём за период. Для неучтённой величины оставьте поле пустым.
   Дату и основание регистрации можно посмотреть в истории.
5. В динамике выберите труд к дате, общую оценку, срок или стоимость.
   Например, 7 зарегистрированных чел·ч при 8 плановых показывают разницу
   в учтённом труде. Вывод о готовности работы требует её результата.
   Под графиком откройте «Значения и источники по датам», затем «Исходные данные»
   нужной версии. Там сохранены O/M/P, календарь, ставки и факты для сверки.

После первой записи работающий дашборд замечает изменения в исходных таблицах
Obsidian и добавляет снимок при изменении расчётных входов. Пока дашборд закрыт,
промежуточные правки не наблюдаются. При запуске он сверяет последнее сохранённое
состояние с текущим. Переоценка меняет прогноз. Для изменения базового плана
РП отдельно записывает новую версию.

### Вкладки и обсуждения

Откройте локальный дашборд и нажмите **«Монитор этапа»**. В строке выбора
укажите этап и, если нужен один пункт, фичу. «Версия документов» переключает
рабочие заметки и снимок конкретной редакции. Скопируйте адрес страницы, чтобы
вернуться к выбранному этапу, пункту, версии и вкладке на действующем сервере.

| Вкладка | Что можно сделать |
| --- | --- |
| Управление | Увидеть охват оценки и поручения РП, внести предложение и принять решение |
| Анализ | Сверить изменения в требованиях, проверить BDD и NFR, задать вопрос о критерии |
| Инженеры | Открыть связанную задачу, конкретный запуск и его лог, сверить проверенную версию правила |
| Совместная работа | Посмотреть передачи между командами, найти адресата открытого вопроса, ответить и вернуть вопрос на обсуждение |

У ранних редакций Чифа сохранилась только карточка. Выберите «Снимок»
и нажмите «Открыть редакцию», чтобы прочесть её. Пометка «нет снимка»
указывает, какие документы тогда ещё не сохранялись. Текущий текст доступен
через «Рабочие документы».

**Задать вопрос.** Выберите фичу либо весь этап, укажите тему, роль автора,
адресата и текст. Если ответ нужен до утверждения оценки, поставьте отметку
«Блокирует решение по этапу». После ответа появится действие «Вернуть на
обсуждение». Его причина останется рядом с предыдущим ответом. Рабочие места
доступны одному локальному оператору. Указанные роли и имена подписывают
действия в журнале. Входа под индивидуальными учётными записями в этом режиме нет.

**Связать инвариант с проверкой.** Нажмите «Связать инвариант с задачей»,
выберите документ и редакцию, скопируйте точную цитату правила. Укажите его
ID, задачу и событие запуска. Если в подробном журнале unittest указаны имя и
исход отдельного теста, можно ввести полное имя. На схеме будут доступны
цитата и её отпечаток, исходник, задача и журнал. Исторический запуск
остаётся привязан к той версии правила, которую выбрал автор связи.

**Переоценить этап.** На вкладке «Управление» раскройте форму переоценки,
укажите основание и сохраните предложение. У РП есть ручное решение и режим
автоматического согласования изменений трудозатрат. Сначала РП утверждает
полную исходную оценку. Затем для автоматического режима указывает допуск в
чел·ч и срок полномочий. При изменении границ, пропусках, открытом блокирующем
вопросе или выходе за допуск требуется решение РП. Устаревшее предложение
можно пересчитать и связать с предыдущим через поле «Связь с прежней оценкой».
Время работы агента и число тестов имеют свои источники. Фактическому труду
людей, доступной ёмкости и стоимости нужны отдельные исходные записи.

Если одно событие риска затронуло несколько фич, в разделе «Риски» **этапа**
можно явно указать общий источник надбавки. Локальные коды R1 двух фич
сами по себе описывают разные записи. Пример заполнения:

| Общее событие | Риски фич | Где учтено |
| --- | --- | --- |
| Недоступна общая тестовая база | search/R1, export/R3 | search/R1 |

**Пример Чифа.** В этапе «Проектная документация» на вкладке «Совместная
работа» откройте связь FR-23. Она ведёт от правила повторного обсуждения
к конкретному тесту и журналу его прогона. В «Управлении» у этапа известны
15,3 чел·ч по одной полностью оценённой фиче из шести. Предложение
осталось на рассмотрении, полный итог требует данных остальных фич.

## От плана к повторной доработке

1. Чиф переносит согласованные этапы и фичи в карточки. На главной заметке
   нажмите название этапа. Внутри видны фичи и ссылки «Доработать этап» и
   «История редакций». В карточке каждой фичи есть ссылка «Доработать фичу».
2. Откройте доработку из карточки или через «Рабочее место → Запросить доработку».
   Под заголовком «Что изменить» напишите желаемое поведение
   и как его проверить. Например, «при экспорте CSV сохранить строки с пустой
   ценой; проверить на ведомости с одной такой строкой». Отметьте «Передать Чифу».
3. Через локальный наблюдатель Чиф сохраняет заявку и передаёт её в настроенную
   для проекта среду. В разделе «Квитанции» откройте новую запись. В ней есть ID
   заявки и подтверждение сессии либо причина сбоя. При работе в Codex или Claude
   текущий Чиф также может взять запись из очереди командой `pending`. Автоматическая
   доставка использует шлюз проекта — OpenCode или Pi.
4. После проверки в истории появляется новая редакция. В ней указаны запрос,
   результат и основание приёмки. У этапа сохраняется состав фич при постановке
   и при приёмке. Ссылка «Предыдущая редакция» ведёт к прежнему состоянию.
5. Для следующего изменения снимите отметку, сохраните заметку, подготовьте
   новый текст и снова отметьте строку. Открытие той же карточки и чтение
   прежнего результата доступны без обращения к модели.

Наблюдатель запускается при открытии базы через комплект. После перезагрузки
компьютера снова откройте её этим способом. Вручную введённые заметки и ещё
не обработанные отметки сохраняются на диске. Отдельные плагины Obsidian
для передачи не требуются.

## Команды для Чифа и разработчика

Из корня проекта на Windows можно повторить настройку, добавить этап и
фичу, затем открыть рабочее место фичи. На Linux используйте
`sh kit/python.sh` вместо `.\kit\python.cmd`.

```powershell
.\kit\python.cmd -m kit.project_docs init
.\kit\python.cmd -m kit.project_docs add stage --key reports --title "Отчётность"
.\kit\python.cmd -m kit.project_docs add feature --key export-csv --parent reports --title "Выгрузка CSV"
.\kit\python.cmd -m kit.project_docs open --key export-csv --section workspace
.\kit\python.cmd -m kit.project_docs open --key export-csv --section requirements
.\kit\python.cmd -m kit.project_docs open --key export-csv --work
```

Для `--section` доступны `workspace`, `requirements`, `bdd`, `nfr`, `effort`, `risks`, `estimate`.
`--work` по-прежнему открывает черновик заявки. При обновлении уже запущенного
наблюдателя выполните `stop` и откройте базу через комплект ещё раз.

При доработке Чиф читает очередь и сохраняет итог. Подставьте ID,
выданный этой заявке, в команды ниже.

```powershell
.\kit\python.cmd -m kit.project_docs pending
.\kit\python.cmd -m kit.project_docs compare --request ID
.\kit\python.cmd -m kit.project_docs accept --key export-csv --request ID --task ID --result "Выгрузка сохраняет строку с пустой ценой" --evidence "Проверена контрольная ведомость"
```

Проверка по журналу требует завершённой задачи и успешного полного прогона.
При личной проверке результата оператор может явно указать `--manual`
и описать, что проверил. История сохраняет это основание. Если пользователь
менял карточку, черновик или один из пяти документов после подачи заявки,
Чиф показывает расхождение командой `compare`. После сверки можно отправить новую
редакцию. Прежние заявки доступны в исходном объёме: в них не добавляются задним
числом условия, которых не было при постановке. Если документ уже созданной фичи
пропал, восстановите его по указанному в сообщении пути из копии или из снимка
принятой редакции. Комплект не подставляет пустой шаблон вместо утраченного текста.

- **Без окна.** `init --no-open` создаёт базу без установки приложения и запуска
  наблюдателя. `submit --key KEY` сохраняет текст в очередь. `send --request ID`
  передаёт сохранённую заявку и публикует квитанцию.
- **Перенос.** Закройте окно этой базы, выполните `stop`, перенесите всю её папку
  вместе со скрытой `.chief/` и выполните `init --vault "новый путь"`. При переносе
  репозитория сохраните его файл `.chief-project.json`. Привязка сверяется по ID.
- **Сбой доставки.** Если служба была недоступна, выполните команду повтора из
  квитанции. После обрыва во время отправки откройте указанную сессию и сверьте
  историю сообщения. Кит сохраняет его ID и не начинает вторую работу вслепую.
## Режим проекта и очередь исполнителей

Откройте дашборд из каталога установленного проекта командой
`.\kit\python.cmd -m kit.dashboard.launcher`. Под выбором задачи переключатель
**Режим Чифа** действует на этот проект. При новой установке Чиф выключен.
Можно просто запустить свой `opencode`, `pi`, `codex` или `claude`.
Единая точка запуска тоже принимает аргументы обычного CLI, например
`.\kit\python.cmd -m kit.run_agent opencode -- --version`.
В Linux используйте `sh kit/python.sh` вместо `.\kit\python.cmd`.

При включении кит сохраняет обычные инструкции проекта и подключает правила
Чифа. При выключении он закрывает приём работы, запрашивает паузу своих команд
и возвращает обычные файлы. Отметки отправки в Obsidian остаются до включения.
Уже открытый вручную чат может помнить загруженные инструкции. Откройте новую
сессию, чтобы прочитать выбранный профиль. Переключатель доступен и без открытой задачи.

Пример для проекта, где есть файл `src/price.py`. Замените путь и текст задания
на свои. Для Claude Code укажите `--agent claude`.

```powershell
.\kit\python.cmd -m kit.chief_mode on
.\kit\python.cmd -m kit.native_team --task price-review create --agent codex
.\kit\python.cmd -m kit.native_team --task price-review enqueue --role executor --file src/price.py --instructions "Исправь округление суммы до двух знаков."
.\kit\python.cmd -m kit.dashboard.launcher --task price-review
```

Перед запуском очереди укажите модель Codex в `CHIEF_CODEX_MODEL`. Для
OpenAI используется `OPENAI_API_KEY`, адрес совместимого локального Responses API
задаётся через `CHIEF_CODEX_BASE_URL`. Для Claude Code подготовьте
`ANTHROPIC_API_KEY` или `ANTHROPIC_AUTH_TOKEN`. Можно задать `ANTHROPIC_MODEL`
и адрес сервиса `ANTHROPIC_BASE_URL`. Диспетчер читает переменные своего
процесса. После изменения окружения перезапустите дашборд. Проверить установленный
CLI и поддержку управления на машине можно через `kit.project_docs probe --agent codex`
или `--agent claude`.

В выбранной задаче нажмите **Запустить очередь**. Рабочая копия содержит
назначенный файл и документы, явно переданные через повторяемый параметр
`--contract`. Исполнитель возвращает содержимое одного файла. После проверки
результата оператор переносит его в проект. Если исходник или контракт изменился,
перенос потребует нового поручения на актуальной основе.

Перед переносом выполните `kit.native_team --task <ID> status` через комплектный
Python. Для каждого завершённого инженерного поручения результат содержит
`workspace`, `assigned_file`, `baseline_hash` и `candidate_hash`. Откройте
файл из `workspace` рядом с исходником в своём редакторе. Например, при проверке
самого Чифа модель вернула исходный текст модуля без завершающего перевода
строки. Различие видно по отпечатку. Кандидат оставлен в рабочей копии.

| Действие | Что произойдёт |
| --- | --- |
| Пауза | Запуск новых ходов закрывается. Чиф ждёт подтверждения остановки активных групп от ОС. Ожидающие поручения сохраняются. |
| Снять поручение / очистить очередь | Снимается выбранная ожидающая запись или все ожидающие записи. Уже выполняющиеся ходы продолжаются. |
| Лимит провайдера | Команда переходит на паузу, ожидающие поручения снимаются. Для прерванных нужна сверка. |
| Сверить после сбоя | Чиф находит активные попытки предыдущего диспетчера и проверяет их остановку. Для каждой можно выбрать повтор, снятие или публикацию уже сохранённого кандидата. |
| Продолжить | После решения по прерванным попыткам приём открывается снова. Для исполнения оставшихся поручений запустите очередь. |

Те же действия доступны через `kit.native_team --task <ID>` и команды
`status`, `pause`, `recover`, `retry --job <UUID>`, `discard --job <UUID>`,
`publish --job <UUID>`, `resume`, `run`, `drop --job <UUID>`, `clear`,
`cancel` и `integrate --job <UUID>`. Публикация завершает запись в рабочую копию.
Перенос меняет файл основного проекта. Заявка из Obsidian,
отправленная через `project_docs send`, продолжает открывать свой одиночный
корневой ход и его квитанцию.

Если при выключении показано «Требуется завершить переключение», прочитайте
причину в дашборде. После прерывания обмена файлами повторите **то же направление**
переключения. При расхождении хешей сообщение указывает сохранённые пути для сверки.
Для старой прямой отправки без сведений о группе процессов и без квитанции
потребуется проверить исходную сессию. До подтверждения дашборд показывает
незавершённое выключение.
## Передача файла исправителю (AC-04)

Из корня Чифа создайте команду. Параметр `--test` ставится последним.
В приведённом примере тест и модуль уже входят в проект.

```powershell
.\kit\python.cmd -m kit.native_team --task quota-review create --agent codex
.\kit\python.cmd -m kit.native_team --task quota-review enqueue --role executor --file kit/provider_limits.py --contract kit/tests/test_provider_limits.py --instructions "Проверь обработку структурированных ошибок HTTP 429 по приложенному тесту." --max-attempts 3 --fixer-attempts 2 --test python -m unittest kit.tests.test_provider_limits
.\kit\python.cmd -m kit.dashboard.launcher --task quota-review
```

Для Claude Code замените `--agent codex` на `--agent claude`. Нажмите
**Запустить очередь**. Чиф проверяет кандидата на изолированном снимке.
В снимок входят назначенный файл и перечисленные контракты. Перечислите
импортируемые проектные модули теста отдельными `--contract`. В этой
версии поддержаны тесты Python `unittest` со стандартной библиотекой.

При нарушении утверждения дашборд показывает ID теста и первую попытку.
Исправитель получает точный текст отклонённого файла, замороженные контракты,
результат теста и прежнее требование. Любая следующая реализация проходит тот же тест.
При указанных лимитах после первого провала остаются **2 из 3 общих** и
**2 из 2 исправительных**. Чиф считает подтверждённые провалы реализаций.
Успешная проверка расходует время и токены, число оставшихся исправлений сохраняется.
Если лимиты опущены, Чиф фиксирует действующую политику при постановке поручения.

Ошибка импорта, неполный или пустой набор и остановка проверки требуют решения.
Попытки исправления при этом сохраняются. После устранения причины выберите
повторную проверку в карточке и запустите очередь. При зелёном результате
проверьте изменения и нажмите **Перенести в проект**. После обычной приёмки
`kit/task_metrics.py finish --task quota-review` создаёт
`.metrics/quota-review/report.md` и открывает доступ к отчёту из карточки.
Он показывает каждую попытку, результаты тестов, остатки бюджета и доступные
счётчики CLI. Если лимит исчерпан с красным тестом, история остаётся на экране,
а файл проекта сохраняет прежнее содержимое.

## Отказ провайдера (AC-05)

В дашборде выберите задачу и откройте её панель **Команда проекта**.
Если указана **Ошибка API провайдера**, активные участники остановлены после
подтверждения ОС, ожидающие поручения сохраняются. При исчерпании квоты
ожидающие поручения снимаются. В строке инцидента видны номер запуска CLI и
модель, если её удалось определить. Счётчик запусков включает повтор после
отказа. Бюджет исправлений расходуется при провале приёмочного теста.

1. Проверьте доступ к указанной модели. В карточке с полученным файлом нажмите
   **Скачать файл для сверки**. Кнопка скачивает текстовую копию с исходными
   байтами. Если провайдер отказал до передачи файла, карточка покажет
   **Файл не получен**.
2. После восстановления доступа верните прерванное поручение в очередь или
   снимите его. Примите решение по каждому прерванному поручению. Возобновите
   команду и запустите очередь. При повторе Чиф использует модель, имя которой
   сохранилось при постановке поручения или первом отказе.
3. Примите итоговую версию по обычному тесту. В завершённой задаче раздел
   **Отказы провайдера** сохраняет причину и сведения о доступном файле.
   Предыдущую копию можно скачать и после успешного повтора.

В CLI используйте ID задачи, UUID поручения и номер запуска из его карточки.
Параметр `--output` задаёт новое имя копии для сравнения.

```powershell
.\kit\python.cmd -m kit.native_team --task $task partial --job $job --attempt 1 --output .\received-attempt-1.txt
```

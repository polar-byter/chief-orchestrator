# Как оценивать трудозатраты, срок и ресурсы

Методика к FR-16 использует разделы 3–4 учебника v4. Ей можно пользоваться
в документе «Оценка трудозатрат» рабочего места фичи в Obsidian. Там сохраняются
исходные значения, формула, основание и факт. Сохранение таблицы пересчитывает
PERT v1 и разброс для каждой работы, сумму и утверждённый отдельный резерв.
Оценку составляет инженер по поручениям, аналитик уточняет спорные
условия, РП сводит работы с календарём и бюджетом.

## Что сохранять вместе с числом

Для каждой строки нужны ID задачи и редакция объёма, исполнитель или роль,
единица, перечень включённых работ, три исходных значения, источник и дата.
Основанием может быть фактическое время похожей задачи либо экспертная оценка
с явно указанным допущением. В последнем случае РП указывает, какое наблюдение
позволит уточнить прогноз. После изменения контракта создаётся новая редакция.

| Величина | Единица | Откуда берётся |
| --- | --- | --- |
| Труд человека | чел·ч по роли | Анализ, проектирование, реализация, ревью, исправления, проверка и документация в названных границах |
| Работа агента | минуты занятия слота, входные и выходные токены | Прогноз по похожим попыткам, факт по журналу и доступным данным провайдера |
| Календарная длительность | рабочие или календарные дни с датой начала | Зависимости, рабочий календарь, доступность людей и слотов, время ожидания решения |
| Стоимость | сумма в указанной валюте и период | Труд по ставкам, API по отдельным тарифам, вычисления и хранение по необходимости |

Длительность открытой задачи включает ожидание. Для учёта фактически
потраченных человеко-часов требуется запись времени человека. Если журнал
содержит только начало и конец задачи, труд остаётся неизвестным.

## Пример расчёта по трём точкам

Рассмотрим учебную задачу «Подтвердить остановку семейства сессий». В оценку
включены уточнение контракта, реализация, проверка ошибки API и обновление
руководства. Все три числа относятся к одному объёму и выражены в чел·ч.

| O, оптимистично | M, наиболее вероятно | P, пессимистично |
| --- | --- | --- |
| 8, существующий вызов достаточен | 12, потребуется уточнить ответ среды | 24, потребуется разобраться с неопределённым результатом вызова |

Средняя оценка PERT равна `(O + 4 × M + P) / 6 = 80 / 6 ≈ 13,3 чел·ч`.
Разброс по приближению PERT составляет `(P − O) / 6 ≈ 2,7 чел·ч`. Для заявления
о вероятности уложиться в конкретный срок нужны модель распределения и данные.
В карточке остаются все три значения. Расчёт ведётся до округления, в примере
отображается один десятичный знак.

Проверки входа допускают конечные числа в порядке `0 ≤ O ≤ M ≤ P`; ноль допустим
для действительно отсутствующей работы. Пустое поле означает «Нет данных».
При разных единицах или неполной тройке расчёт ждёт уточнения. Если O = M = P,
результат равен M, разброс равен нулю в рамках этой оценки.

Правило трёх частей из §3.1 помогает обнаружить забытый этап. Если инженер
оценил только код, РП запрашивает труд на спецификацию и проверку. При ранней
прикидке допустимо явно принять равные доли и записать это как допущение.
В нашем примере 13,3 чел·ч уже охватывают весь цикл. По мере снятия
неопределённости РП заменяет доли оценками конкретных работ и хранит прежнюю версию.

## Когда работа закончится

Для доступной ёмкости берём сумму по людям. Для каждого умножаем рабочие дни
на часы в день, выделенную проекту долю ставки и долю времени на проектную
работу. Например, пять дней по восемь часов при полной занятости в проекте и
фокус-факторе 0,65 дают 26 чел·ч. Коэффициент уточняется по факту команды.

При одном доступном инженере и 5,2 продуктивного часа в день пример занимает
около 2,6 рабочего дня при немедленном старте и отсутствии ожидания. Для плана
из нескольких задач РП размещает каждую после зависимостей и при наличии нужной
роли. Две независимые проверки по четыре часа можно закончить за четыре часа
при двух доступных проверяющих. Для одного проверяющего понадобится восемь.
Для агентов отдельно учитываются число слотов, занятость, повторные попытки и
лимиты провайдера. Ожидание согласования может сдвинуть дату без роста чел·ч.

## Ресурсы и сверка с фактом

Для API отдельно суммируются прогнозные входные и выходные токены по модели,
числу задач и ожидаемым итерациям. Для тарифа за миллион токенов стоимость
равна `(вход × цена входа + выход × цена выхода) / 1 000 000`. У тарифа
сохраняются валюта, дата и источник. Неизвестный тариф оставляет стоимость
открытой. Вычисления и хранение включаются, когда их требует сценарий нагрузки.
Например, оценка vCPU использует процессорное время запроса, пиковый RPS и
целевую загрузку. Для N+1 проверяют оставшуюся мощность после потери одного узла.

В «Рабочем месте» рядом с каждой оценкой доступны её охват, формула, входы,
связанные риски и фактические данные той же размерности. В обзоре РП видит
сумму по непересекающимся работам, период и долю работ с известной оценкой.
Сумму с пропусками следует помечать как частичную. По завершении сравниваются
план и факт, записывается объяснение отклонения для следующих оценок.
Правила учёта резерва описаны в [методике рисков](RISK_ASSESSMENT.ru.md).
Критерии приёмки расчёта приведены в [спецификации](UNIVERSAL_KIT_SPEC.ru.md).

В мониторе этапа метод `stage-resources-v1` использует точные значения PERT
по каждой работе. Ставка относится к продуктивному человеко-часу. Спрос
по команде включает назначенные ей работы и отдельные резервы. Для резерва
у работ одной роли наследуется эта роль. При нескольких ролях РП назначает
команду в плане. Если команду или цену для ненулевого объёма ещё предстоит
уточнить, сводка показывает доступную часть.

Ёмкость периода считается включительно по датам и выбранным рабочим дням.
Загрузка в процентах равна `100 × спрос / ёмкость`. При нулевой ёмкости
процент определить нельзя. Дата окончания получается из расписания команд
с учётом связей и ожидания. Все исполнители одной роли образуют общий фонд
часов. Такая модель подходит работам, которые команда может распределить
между своими участниками. Нерабочие даты РП вводит для конкретного проекта.

График сравнивает накопленный труд по сохранённому расписанию к концу даты
с зарегистрированными часами. Трудовые затраты, расходы по табелю и тарифы API
имеют разные источники. Бюджет этапа включает оценку труда по ставкам, токены по
двум тарифам и прочие расходы в валюте плана. Факт в разных валютах хранится
по исходным записям. Для прогноза срока требуется актуальный объём работ и
доступность команд. Записанное время само по себе не определяет остаток работы.
[Формы РП и динамика](../user/PROJECT_DOCUMENTATION.ru.md#ресурсы-всего-этапа).

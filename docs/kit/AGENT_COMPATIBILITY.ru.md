# Общий кит для OpenCode, Pi, Codex и Claude Code

Состояние исходников проверено 14 ноября 2026 года. Этот документ фиксирует
исходные версии и результат первой интеграции в рабочей ветке.
Требования и задачи находятся в [живой спецификации](UNIVERSAL_KIT_SPEC.ru.md),
порядок разработки — в [описании методологии](DEVELOPMENT_METHOD.ru.md).

## Назначение и границы работы

Кит организует полный цикл разработки по пользовательскому заданию. Чиф читает
документы и существующий код, разбивает проект на согласованные модули,
фиксирует контракты и зависимости, готовит заготовки и тесты. Исполнители
реализуют поручения в отдельных копиях. Контроллер ограничивает работу,
Чиф проверяет результат, а принятые изменения последовательно объединяются.
Bug Fixer продолжает исправления в рамках сохранённого бюджета.

Доработка развивает существующий инструмент целиком. Сокращение продукта до MVP
не является целью и не должно автоматически сокращать исходные требования.
Порядок небольших проверяемых этапов нужен для переноса существующих возможностей
без потери поведения, а не для исключения функций из итогового результата.

В отдельных тестовых проектах использовалась локальная Qwen3-4B-Instruct-2507.
Для Windows проверены следующие пути.

| Среда | Что прошло через реальный процесс |
| --- | --- |
| OpenCode Desktop CLI 2.2.6 | Служба проекта, корневой Чиф, дочерний исполнитель и ещё один ход в исходной сессии. По завершении шлюз вернул то же семейство и пустую очередь |
| Pi 1.3.0 из комплекта | ProjectPiBroker запустил Чифа и изолированного исполнителя. Повторный вопрос пришёл в ту же беседу. Прочитаны действительные ответы и показатели токенов |

| Claude Code 2.1.325 | Два процесса, один UUID. Второй процесс воспроизвёл одноразовый маркер первого сообщения. Бинарный файл установлен в каталоге проверки |

Команда `project_docs probe --agent codex` или `--agent claude` проверяет
справку установленного CLI. Работоспособность модели подтверждается ответом на
отдельную заявку. Одиночная доставка покрывает корневой ход агента.
Для инженерной команды используется `kit.native_team`, ей принадлежат своя
очередь, процессы и рабочие копии. Сценарий AC-04 проверен на задаче
классификации HTTP 429. На отдельных установках Чифа Codex CLI и Claude Code
с локальной Qwen передали исправителю отклонённую реализацию и два оставшихся
исправления. В каждом успешном прогоне первая попытка провалила утверждение,
вторая прошла тот же тест. Перенос и итоговый отчёт проверены через штатную
команду и дашборд. Отдельный прогон Claude Code показал остановку после двух
неудачных исправлений с остатком 0/0. Эти живые проверки проведены в Windows.

Для AC-05 оба установленных CLI получили от локального HTTP-стенда отказ 503
и квоту 429 при работе с файлом Чифа. Состояние соседнего поручения оказалось
соответственно «В очереди» и «Отменена». После восстановления API оба CLI по
решению оператора прошли тест исходной моделью, хотя её имя в окружении уже
изменилось. В двух отдельных сценариях файл был доступен до отказа. Для Codex
это сообщение в завершившемся ошибкой Responses API, для Claude — сообщение
перед обрывом потока. Из обоих дашбордов в Edge скачаны ожидаемые 912 байт.
Приёмка проверяет обработку управляемых отказов и сохранность данных в Windows.

Для Codex и Claude Code пройден также пользовательский путь `configure → submit
→ send` в двух отдельных проектах. В обоих случаях CLI ответил `READY`,
подтвердил UUID, вернул код 0 и показатели токенов. Второй вызов `send` для
той же заявки прочитал прежнюю квитанцию. В выводе `probe` режим `chief_turn`
обозначает одиночную доставку. Поля `worker_guarantees` относятся к этой
доставке. Для управляемой команды смотрите отдельный результат `managed_team`.
Проверка возможностей CLI и ОС обходится без вызова модели.

### Инженерные поручения U-06 и U-07

На копиях исходного проекта под Windows проверены два настоящих клиента с
локальной Qwen. У каждого клиента одновременно исполнялись два поручения.
В каждой группе было по четыре процесса. После подтверждения паузы в обеих
группах осталось ноль. Третье поручение сохранилось в очереди. Отдельно
проверены прерывание диспетчера, восстановление с решением оператора,
перенос кандидата по совпавшей основе, отказ после изменения основы и
сохранность соседнего файла. При ответе HTTP 429 от контрольного сервиса
клиент послал один запрос, активная попытка была прервана и ожидающее поручение снято.

В свежей установке Windows все четыре обычных CLI запускались и сразу после
установки, и после цикла `on → off`. OpenCode Desktop CLI 2.2.6 прочитал имя из
обычной конфигурации. Также проверены Pi 1.4.0 из PATH, Codex CLI
0.166.0-alpha.5.1 и Claude Code 2.1.325. После переключения содержимое 12 файлов
пользователя совпало с исходным побайтово. В Edge выполнено 19 действий и проверок
с реальной очередью Codex. На самом Чифе завершились два поручения, в том числе
для `kit/runtimes/__init__.py`.

На чистой Ubuntu 24.04.5 отдельно прошли шесть проверок системного контроля
процессов. В них участвовали настоящий дочерний процесс и его потомок. Для
инженерной команды нужны пользовательский systemd, cgroup v2 и Landlock ABI 3
или новее. Проверка двух клиентов с моделью проведена в Windows.

При прямой доставке из Obsidian оба CLI продолжили разговор по ранее полученному
UUID. На третьем ходе выключение режима остановило два зарегистрированных процесса
каждого CLI. Оператор получил неопределённый исход. Повторная отправка той же
заявки сохранила результат сверки и не обратилась повторно к модели.

Эти операции требуют запуска через управляемую команду Чифа. В режиме
`off` каждый из четырёх агентов открывает обычную сессию пользователя.
[Команды и поведение очереди](../user/PROJECT_DOCUMENTATION.ru.md#режим-проекта-и-очередь-исполнителей).

Pi-репозиторий основан на исходном коммите OpenCode
`03c128d7fd46e4b1346d37c0521b4b6cb4ea3361`; это не взаимозаменяемые копии одного
актуального дерева. Переносить его файлы поверх основного репозитория целиком
без сравнения последующих исправлений нельзя.

Доступ к моделям провайдера и поддержка среды агента — разные возможности.
Вызов модели Anthropic по API сам по себе не делает кит плагином Claude Code.
Аналогично доступ к модели OpenAI не подтверждает интеграцию с Codex.

## Как сейчас проходит задача

1. Вход — текущий запрос пользователя либо существующий `TASK.md`. Чиф сам читает
   доступные документы. Файл задания необязателен, а текущий явный запрос имеет приоритет.
2. План — обязанности модулей, публичные интерфейсы, зависимости, общие типы,
   форматы данных и применимые ограничения. Архитектура и реестр функций
   публикуются для дашборда.
3. Поручение — заготовка одного связного исходника, тесты и зафиксированные
   требования. Контроллер создаёт изолированную копию и точную сессию исполнителя.
4. Исполнение — проверка разрешений, подтверждённый запуск наблюдения,
   ограничение шагов, времени и повторений. По умолчанию доступны два места
   для независимых готовых работ; сохранённый выбор пользователя важнее умолчания.
5. Завершение попытки — подтверждённая остановка, `inspect`, чтение кода,
   тесты именно этой копии, доказательства по каждому требованию и `review`.
6. Исправление — Bug Fixer при дефекте реализации или допустимом сигнале лимита.
   Ошибка API, настройка среды, пауза и отмена не подменяются дефектом кода.
7. Объединение — только принятого файла и только при неизменных исходном файле
   и общих контрактах. Готовность зависимости требует приёмки и интеграции.
8. Завершение задачи — проверка настоящего интерфейса, если он есть, полный
   набор тестов объединённого проекта, запускаемый результат и замороженный отчёт.

Журнал, пауза, продолжение, отмена, восстановление и дашборд относятся ко всему
циклу. Они должны сохраняться при смене среды выполнения.

## Что уже можно использовать повторно

Общее поведение представлено в `journal.py`, `delegation_guard.py`,
`loop_guards.py`, `suite_runner.py`, `execution_policy.py` и связанных проверках
приёмки в `task_metrics.py`. Эти модули являются кандидатами общего ядра;
их зависимости ещё нужно проверить при выделении. Название модуля не доказывает
его полной независимости от OpenCode.

При сравнении 14 ключевых модулей побайтно совпали `journal.py`,
`loop_guards.py`, `suite_runner.py`, `execution_policy.py`, `execution_watch.py`,
`dashboard/session_control.py` и `installer.py`. Различаются
`delegation_guard.py`, `task_metrics.py`, `execution_controller.py`,
`usage_report.py`, `model_switch.py`, `dashboard/controls.py` и `run_opencode.py`.
Совпадение исходников не заменяет проверку поведения в разных средах.
Список сравнения с SHA-256 сохранён в журнале исследования
`.metrics/universal-project-skill-20261114/core-comparison.json`.

Примеры существенных различий: Pi исключает `.tools` и `.pi` из снимка,
добавляет выбор шлюза в управление задачей, получает историю через службу Pi
и выбирает соответствующий файл подготовленной конфигурации при смене модели.
Это требует явного решения при переносе, а не механического объединения файлов.

В Pi-адаптации уже есть полезная граница:

```text
правила задачи, журнал, приёмка, бюджеты и интеграция
                         |
              шлюз выполнения среды
                 /                \
        OpenCode service      Pi project broker
```

`runtime_selection.create_session_gateway()` выбирает шлюз без запуска службы
при импорте. `load_project_model_choices()` отделяет выбор моделей.
`PiSessionControl` обращается к службе, которая владеет процессами Pi и связывает
их с задачами. Это существующая основа для переноса, а не повод заново писать
оркестратор.

### Изменения в рабочей ветке после обследования

При трёхстороннем сравнении учтены 312 путей. Содержимое 178 совпало между
вершинами, 128 различий принадлежат ветке Pi, ещё шесть путей менялись с
обеих сторон. Среди них — контроллер и команды журнала. Перенесена общая
точка выбора среды, Pi-брокер, RPC, ограничения файлов и экспорт истории.
У OpenCode сохранён исходный режим по умолчанию. В новой конфигурации
совместный протокольный набор прошёл 91 тест, включая запуск настоящего
Pi 1.3.0 без вызова модели. Последующие запуски с моделью описаны в таблице
выше. [Настройка и запуск Pi](../user/PI_QUICKSTART.ru.md).

Исходная карта привязок на момент обследования:

- `execution_controller.py` создаёт `SessionControl`, проверяет корневую сессию
  OpenCode и вызывает операции её API.
- `dashboard/controls.py` управляет деревом через `SessionControl`.
- `usage_report.py` получает историю и токены из экспортов OpenCode.
- `run_opencode.py`, `model_switch.py` и конфигуратор используют выбор и
  надстройку `.opencode`.
- `installer.py` ищет OpenCode Desktop и поставляет его настройки и команды.
- `AGENTS.md`, команды и промпты содержат инструкции, зависящие от этой среды.

## Целевая форма поставки

Рекомендуемая архитектура — общее ядро, переносимый скилл Чифа и адаптеры сред.

**Общее ядро** владеет задачей, попытками, требованиями, журналом, лимитами,
приёмкой и интеграцией. Смена среды не меняет правила успешного завершения.

**Скилл** объясняет Чифу чтение проекта, декомпозицию полного задания, контракты,
выдачу поручений и проверку результата. Он вызывает инструменты установленного
кита и сохраняет действующие разрешения пользователя. Копирование `SKILL.md`
само по себе не переносит создание сессий, отмену, права, дашборд и расход.

**Адаптер среды** отвечает за точную привязку сессий, передачу задания, публичные
события, модели и историю, ограничение инструментов, очистку очереди и
подтверждённую остановку. Возможности необходимо обнаруживать и проверять.
При отсутствии необходимого контроля следует сообщать конкретное ограничение,
а не выдавать уменьшенный набор гарантий за полную совместимость.

**Поставка для среды** добавляет её точки входа, манифесты, команды или расширения.
Формат установки и API плагинов нельзя считать одинаковыми для всех агентов.

### Предложение для U-08. Одна установка Чифа

В рабочей редакции 14 реализованы общий мастер, выбор агента, запуск
из папки проекта и чтение обоих прежних манифестов. Описание исходных
различий ниже относится к обследованным версиям. [Установка, миграция и выпуск](../user/DISTRIBUTION.ru.md).

15 ноября 2026 года сверены публичные вершины OpenCode `329bda1` и Pi
`dd7e296` и текущая рабочая ветка Чифа. Исходники Pi происходят от коммита
`03c128d` основного кита. В рабочей ветке уже есть общий дашборд, проектная
база, подключённый брокер Pi и управляемые команды Codex и Claude Code.
В версии OpenCode `329bda1` кнопка установки зависела от наличия Desktop.
В версии Pi `dd7e296` были собственные мастер, подготовка среды
и модуль обновления `kit/pi_project_update.py`. Обновление прежнего проекта
теперь выполняет [общий установщик](../user/DISTRIBUTION.ru.md).

**Рекомендуемая схема.** Один репозиторий разработки ядра, одна версия
поставки и один мастер для пользователя. При установке пользователь выбирает
папку проекта и нужные среды. Мастер проверяет зависимости каждой выбранной
среды и сообщает, какие действия доступны. В проекте одна очередь каждого
управляемого задания, одна база Obsidian и общий дашборд. Адаптеры отвечают
за собственные CLI, сессии и остановку процессов. Переключение Чифа в режим
`off` возвращает обычный запуск агента.

| Шаг перехода | Условие приёмки |
| --- | --- |
| Общий мастер поверх действующих адаптеров | На чистом профиле отдельно устанавливаются Pi, Codex и Claude Code при отсутствии OpenCode Desktop. С одним OpenCode сохраняется прежний сценарий. Повтор установки в тот же проект идемпотентен. |
| Обновление действующих проектов | Мастер распознаёт оба прежних манифеста, `.metrics/.kit-installation.json` и `.metrics/.pi-kit-installation.json`. На копии проекта сохраняются пользовательский код, настройки моделей, журналы, ID и привязка Obsidian. Изменённые пользователем файлы доступны для сверки. |
| Проверка работы | В одной базе и одном дашборде выполняется назначенная задача через каждый поддержанный адаптер. Проверены заявленные возможности, переключение режима и повторное открытие существующей задачи. |
| Переход пользователей Pi | Пользователь скачивает общий комплект из Releases основного репозитория и выбирает прежнюю папку проекта. Инструкция перехода входит в [руководство по установке](../user/DISTRIBUTION.ru.md). |

Сохранение двух самостоятельных продуктовых веток оправдано, если Pi нужен
собственный жизненный цикл продукта и отдельная команда сопровождения.
Для одного Чифа это удваивает число мест, где надо исправлять правила очереди,
приёмки, отчётов и миграций.
Скилл и его вспомогательные материалы следует поддерживать из одного исходника,
без четырёх расходящихся копий правил.

## Последовательность доработки

1. Сопоставить две актуальные реализации и составить перечень различий общего
   ядра, включая исправления после ответвления Pi. Сохранить прежние журналы и
   работающие команды установленных проектов.
2. Зафиксировать общий контракт выполнения и проверки его возможностей.
   Учесть создание и идентичность сессии, права, события, завершение,
   прерывание, очереди, экспорт истории и неизвестные данные расхода.
3. Подключить существующие OpenCode- и Pi-реализации к этому контракту.
   Сверить одинаковый жизненный цикл попытки и регрессии прежнего поведения.
4. Вынести переносимые инструкции Чифа в скилл. Подготовить установку и
   обнаружение скилла каждой средой, сохранив отдельные настройки провайдеров.
5. Реализовать Codex- и Claude Code-адаптеры по их актуальным официальным
   интерфейсам. Проверить возможность подключить уже открытый разговор отдельно
   от возможности запустить управляемую сессию. Не подставлять вымышленный ID.
6. Проверить установку, обновление, восстановление и полный живой цикл во всех
   поддерживаемых средах. Указать проверенные версии и оставшиеся ограничения.

Для каждого этапа обновляются затронутые `AGENTS.md`, промпты, команды,
руководства установки и работы, документация ядра, оба README и заметки Obsidian.
Описания должны следовать реализованному поведению. Исторические отчёты
сохраняют исходные результаты и область применимости.

## Приёмка совместимости

Для каждой среды нужны свидетельства запуска из исходного пользовательского
задания: самостоятельный план Чифа; две независимые работы и соблюдение
зависимостей; ограничение файлов; исправление дефекта через Bug Fixer;
блокировка после ошибки API; подтверждённая пауза и отмена; восстановление после
перезапуска; приёмка и интеграция; реальные тесты; обзор интерфейса; финальный
отчёт. Отдельно проверяются коллизии при объединении, лимиты и сохранность
проектов после обновления. Для режима с одним исполнителем сохраняется
проверка последовательного пути.

Наличие защитного кода или зелёных модульных тестов не заменяет живой прогон.
Прежние отчёты OpenCode и Pi — свидетельства описанных в них запусков, а не
подтверждение новой общей сборки. При первоначальном обследовании изучены
исходники и существующие отчёты. Проверки изменяемых инструкций
учитываются отдельно в журнале задачи и не подтверждают новые адаптеры.

Проверка при первоначальном обследовании: полный набор содержит 695 тестов, 694 прошли,
ошибок и падений нет, один тест создания символической ссылки пропущен из-за
недоступной Windows-привилегии. Кит записал `status=skipped`,
`category=incomplete`; полностью зелёным этот результат не объявляется.
Проверка junction, коротких имён и обычных путей прошла отдельно.
Прогон выполнен вне ограничений sandbox для localhost, с временными проектами
вне исходного кита. Предыдущий неуспешный прогон сохранён в журнале:
ограничения сокетов и тестовых путей не исправлялись изменением кода кита.

При повторной проверке одновременный запуск двух задач выявил ошибку проверки
обычного пути Windows в журнале. После исправления прошли 36 повторов
с двумя процессами. [Разбор в путеводителе](DEVELOPER_GUIDE.ru.md).

## Учебник и официальные форматы

Для общей части выбрана [методика v4](DEVELOPMENT_METHOD.ru.md). Сценарии и
измеримые ограничения переходят в контракты всех четырёх сред. Аналитик
описывает наблюдаемый результат, инженер проверяет его средствами конкретной
среды. РП пересматривает оценку и риск при изменении возможностей среды.
«Рабочее место» и обзор «Три контура» доступны в проектной базе Obsidian
для всех сред, использующих комплект. Тот же проект открывается в локальном
мониторе этапа. Обсуждения, решения РП и ссылки на проверки принадлежат базе
проекта. Проверка монитора на Чифе приведена в путеводителе.
[Границы реализации](UNIVERSAL_KIT_SPEC.ru.md) · [Путеводитель](DEVELOPER_GUIDE.ru.md).

# Общий Agent Kit: спецификация доработки

Редакция 14 от 15 ноября 2026 года. Методическая основа — учебник РП и анализа v4.
Спецификация охватывает развитие существующего кита для OpenCode, Pi, Codex и
Claude Code. «Рабочее место» выбрано основным экраном, «Три контура» — обзором
проекта. В Obsidian доступно рабочее место с пятью документами и автоматическим
расчётом PERT и резерва по рискам. В общей заметке «Три контура» каждая
роль видит открытые поручения и ссылки к исходным разделам фич.
Действующие возможности и границы проверки перечислены в [обзоре сред](AGENT_COMPATIBILITY.ru.md).

**U-06/U-07, условия приёмки.** Оператор отдельно выбирает режим Чифа и
среду агента. При выключенном Чифе сохраняется штатный запуск CLI. Режим
управления охватывает только семейства, запущенные Чифом. Инженер получает
снимок исходника и согласованных контрактов. Право записи ограничено одним
назначенным файлом изолированной копии. Публикация в основной проект требует
отдельной сверки исходной версии. После обычной паузы очередь сохраняется.
После отмены или остановки по лимиту очередь очищается. При сбое менеджер
проверяет завершение процессов и оставшиеся файлы, а оператор решает судьбу
каждого незаконченного хода до возобновления работы.

Для AC-04 поручение связывает неизменяемый тест, исходный файл и бюджет
неудачных реализаций. Подтверждённый провал утверждения списывает одну попытку
и при наличии остатка передаёт отклонённый файл исправителю того же агента.
Ошибки запуска и неполная проверка требуют сверки. После успешного теста
перенос сверяется с исходником первого поручения. Дашборд показывает родителя
и исправление, итоговый отчёт сохраняет результаты и остаток по каждой попытке.

Для AC-05 инженерная команда различает отказ API и исчерпание квоты. Оба
события требуют подтверждённой остановки и сохраняют бюджет исправлений.
При отказе API ожидающие поручения остаются в очереди. При квоте они снимаются.
Оператор видит причину, номер запуска, известную модель и наличие файла для
сверки. Чиф принимает в архив только разобранное предложение для назначенного
пути. Повтор после восстановления доступа требует решения оператора. Итоговый
отчёт сохраняет отказ и результат последующей проверки раздельно.

Для U-08 реализована одна поставка с выбором среды и переходом с двух прежних
установщиков. Сравнение репозиториев и критерии перехода приведены в
[матрице совместимости](AGENT_COMPATIBILITY.ru.md#предложение-для-u-08-одна-установка-чифа).

В приёмке редакции 11 выполнены реальные ходы Codex и Claude Code на Windows,
проверка очереди и переключателя в Edge и шесть проверок управления процессами
на чистой Ubuntu. Полный набор Windows включал 930 тестов. Прошли 929, ошибок и
падений нет. Один тест создания символической ссылки пропущен из-за прав ОС.
Журнал — `chief-native-teams-20261114/test-34b168526383412a909aa6d5dc1d1082.log`.
[Сценарии и проверенные версии](AGENT_COMPATIBILITY.ru.md#инженерные-поручения-u-06-и-u-07).

В этой редакции добавлено ведение проектной документации. Для каждого проекта
Чиф создаёт или подключает отдельную базу знаний. Первая программа для
работы с этой базой — Obsidian. Доставка приложения и первоначальная настройка
хранилища входят в обязанности кита.

## 1. Specify: результат для пользователя

Пользователь подключает кит к программному проекту в OpenCode, Pi, Codex или
Claude Code, задаёт желаемое поведение и получает управляемый полный цикл
разработки. Чиф читает проект, составляет согласованный план, выдаёт проверяемые
поручения, принимает результат и доводит задачу до запуска и отчёта. Назначать
вручную каждый файл, исполнителя или вызов утилиты не требуется.

Объём сохраняет существующие возможности. Очерёдность переноса не исключает
функции из конечного результата. Новые идеи за пределами этого объёма
фиксируются отдельно от текущей работы.

### Функциональные требования

| ID | Требование | Наблюдаемый результат |
| --- | --- | --- |
| FR-01 | Приём задания | Чиф сам читает чат или TASK.md, инструкции и код; фиксирует источник требований, не смешивает посторонние старые задачи |
| FR-02 | Декомпозиция полного задания | Определены обязанности модулей, интерфейсы, зависимости и проверяемые поручения; требования не теряются |
| FR-03 | Контракты и подготовка | До исполнителя готовы необходимые типы, форматы, заготовки, требования и тесты |
| FR-04 | Изоляция и параллелизм | Независимые готовые работы используют сохранённое число мест; исполнители меняют назначенные файлы своих копий |
| FR-05 | Контроль и Bug Fixer | Сохраняются лимиты и бюджеты; дефект реализации и инфраструктурный отказ ведут по разным маршрутам |
| FR-06 | Приёмка и интеграция | Нужны завершение попытки, inspect, проверка требований, тесты нужной копии и accepted review; конфликт не перезаписывает пользовательский файл |
| FR-07 | Управление и восстановление | Пауза, продолжение и отмена действуют на точное семейство; после перезапуска нет слепого повторного выполнения |
| FR-08 | Дашборд и учёт | Видны фактические попытки и исходы; расход не дублируется, отсутствующие данные остаются неизвестными |
| FR-09 | Завершение | Проверены объединённый проект и применимый интерфейс; есть рабочий запуск и один итоговый отчёт |
| FR-10 | Четыре среды | Общие правила имеют один источник; поставка содержит нужные скиллы, команды или расширения и проверяет возможности среды |
| FR-11 | Установка и обновление | Код проекта и локальный выбор сохраняются; несовместимость видна до допуска исполнителя, прежние журналы читаются |
| FR-12 | Сопровождение | Спецификация, код, проверки, инструкции, руководства и оба README согласованы; статус понятен человеку |
| FR-13 | Живая спецификация возможности | У цели, требований, инвариантов, сценариев BDD и паспортов NFR есть автор, редакция и связи с задачами и проверками |
| FR-14 | «Рабочее место» | Из выбранной возможности пользователь открывает требования, сценарии, качество, оценку и риски, доходит до задачи, запуска и основания решения |
| FR-15 | «Три контура» | РП, аналитик и инженер видят состояние одного проекта. Из отклонения в обзоре можно открыть ту же возможность и её исходные данные |
| FR-16 | Трудозатраты и ресурсы | РП сохраняет исходные оценки по видам работ, доступную ёмкость и допущения. Человеко-часы, календарь, работа агентов и деньги имеют отдельные единицы и основания |
| FR-17 | Риски | РП ведёт причины, события, последствия, меры и остаточный риск. Каждый резерв связан с одним основанием и учитывается один раз |
| FR-18 | Решения и полномочия | Видно, кто подготовил объём и смету, кто определил поведение, кто отвечает за архитектуру и кто согласовал конкретную редакцию или выпуск |
| FR-19 | База знаний проекта | При создании или подключении проекта Чиф создаёт либо привязывает отдельное хранилище проектной документации. Карточка проекта открывается из кита и из самой базы. Сохраняются устойчивый ID проекта, расположение базы и привязка к репозиторию |
| FR-20 | Возврат к этапу или фиче | Пользователь открывает проект, выбирает этап или возможность, читает согласованное поведение и последние проверки и начинает доработку этой же записи. Чиф связывает новую редакцию с поручением и дополняет историю после приёмки |
| FR-21 | Доставка Obsidian | Кит определяет наличие приложения, при необходимости получает установщик из официального источника для поддерживаемой ОС, запускает установку, проверяет результат и открывает документацию нужного проекта |
| FR-22 | Переоценка этапа | РП видит действующую оценку и предложение по одной редакции этапа. Ручное согласование и автоматическое решение по сохранённым полномочиям дают видимое основание и запись в истории |
| FR-23 | Обратная связь между ролями | Вопрос связан с этапом, фичей или риском, адресатом и редакцией. Из каждого рабочего места можно спросить, ответить, вернуть на уточнение и увидеть ожидаемое действие |
| FR-24 | Динамика этапа | Рабочее место роли показывает текущие пункты, ответственных, открытые вопросы, план и доступный факт. Из точки графика можно открыть событие или измерение |
| FR-25 | Рабочие места команд и совместный монитор этапа | В одном проекте есть вкладки «Управление», «Анализ», «Инженеры» и «Совместная работа». На общей схеме видны зависимости, замороженные и предложенные части спецификации, инварианты, задачи, проверки и вопросы. Выбранные этап и редакция сохраняются при смене вкладки |

### Сценарии приёмки

| ID | Given | When | Then |
| --- | --- | --- | --- |
| AC-01 | Проект описан в чате, TASK.md отсутствует | Пользователь начинает работу | Чиф сам читает проект и сохраняет полный план без требования создать TASK.md |
| AC-02 | A и B независимы, C зависит от A | Доступны два места | A и B могут идти одновременно; C допускается после приёмки и интеграции A |
| AC-03 | Назначен один исходник | Исполнитель меняет тест, контракт или основной проект | Среда запрещает действие; снимок и inspect дополнительно проверяют границы |
| AC-04 | Реализация неверна | Чиф отклоняет попытку | После подтверждённой остановки Bug Fixer получает прежние требования и оставшийся бюджет |
| AC-05 | Ошибка API или квоты | Наблюдатель разбирает отказ | Дефект кода не выдумывается, модель не подменяется, частичные файлы сохраняются для проверки |
| AC-06 | Активны Чиф и исполнители, в очереди есть сообщения | Оператор запрашивает обычную паузу | Новые поручения блокируются, очередь сохраняется. Статус «Приостановлено» появляется после подтверждённой остановки всего семейства. При отмене или паузе из-за лимита провайдера очередь очищается |
| AC-07 | Остановка не подтверждена или служба перезапущена | Запрошено продолжение | Сначала сверяются сессии и частичные файлы; слепое повторное исполнение не допускается |
| AC-08 | Попытка принята, целевой файл изменился | Запрошена интеграция | Файл пользователя сохранён; конфликт требует разрешения и повторной проверки |
| AC-09 | Реализация завершается | Чиф готовит finish | Пустой тестовый набор, чужой зелёный запуск и неподтверждённый обзор интерфейса не заменяют нужные свидетельства |
| AC-10 | Устанавливается другая среда | Проверяются её возможности | Скилл обнаруживается; сессии и права проверяются отдельно; отсутствие адаптера видно до исполнения |
| AC-11 | Обновляется установленный проект | Применяется новая версия | Код, модели и журналы сохраняются; результат обновления проверяем |
| AC-12 | У возможности есть сценарий, паспорт NFR и запуск по предыдущему порогу | Аналитик меняет порог и сохраняет редакцию | Сохраняются исходные значения и прежний результат. Новая редакция показывает, что нужна проверка, и указывает затронутые задачи, оценки и риски |
| AC-13 | Выбран проект с двумя возможностями | Оператор входит в проект, затем из «Трёх контуров» открывает риск второй возможности | Вход ведёт в «Рабочее место». Переход из обзора открывает раздел рисков второй возможности с тем же ID, редакцией и владельцем |
| AC-14 | На весь цикл указаны O/M/P = 8/12/24 человеко-часа, календарь и тариф неизвестны | РП запрашивает оценку | Показаны 13,3 чел·ч, охват и исходные значения. Срок и стоимость помечены «Нет данных». Значение M вне диапазона отклоняется с указанием поля |
| AC-15 | Возможная задержка API уже учтена в P, вероятность неизвестна | РП связывает риск с оценкой и назначает проверку | Карточка видна в обоих режимах. Вероятность остаётся неизвестной, повторный резерв исключён. После проверки можно записать исход и новую оценку с обоснованием |
| AC-16 | Пользователь согласовал смету и архитектурный контракт определённой редакции | Инженер сдаёт исполнение, затем запрашивается выпуск в продакшн | Видны решения, их авторы, редакции и проверки. Согласование реализации не даёт автоматического разрешения на публикацию. Изменение предмета согласования возвращает затронутое решение на пересмотр |
| AC-17 | Новый проект на поддерживаемой чистой системе без Obsidian | Пользователь создаёт проект с базой знаний | Кит доставляет и устанавливает приложение, создаёт привязку и открывает карточку именно этого проекта. Ход установки и её исход видны пользователю |
| AC-18 | Obsidian уже установлен, в базе есть этапы, принятая фича и собственные заметки | Пользователь повторно открывает проект после перезапуска | Используются имеющееся приложение и та же база. У этапов и фич сохраняются ID, ссылки и история. Личные заметки и другие хранилища сохраняются |
| AC-19 | Фича принята, у её первой редакции есть проверки и решение | Пользователь выбирает её в базе и запрашивает изменение критерия | Открывается «Рабочее место» той же фичи и этапа. Чиф показывает затронутые задачи и проверки. После приёмки обе редакции доступны из исходной карточки с соответствующими результатами |
| AC-20 | Установка прервалась, хранилище перенесено или заметка изменилась во время работы Чифа | Пользователь продолжает настройку либо сохраняет доработку | Кит объясняет конкретный сбой, позволяет повторить установку или восстановить привязку по ID. При конфликте доступно сравнение редакций. Повторное действие не дублирует проект, задачу или запись о приёмке |
| AC-21 | Завершённый этап содержит две принятые фичи | РП открывает карточку этапа, добавляет третью фичу и меняет срок | Чиф создаёт редакцию того же этапа. РП видит затронутые зависимости, оценку и риски. Результаты первых двух фич доступны в истории. Повторная проверка назначается тем критериям, которых касается изменение |
| AC-22 | В базе завели фичу или открыли карточку предыдущей версии | Оператор открывает из карточки требования, BDD, NFR, оценку и риски и возвращается к фиче | Все пять документов принадлежат выбранному ID, доступны для редактирования и ведут обратно. Заявка сохраняет их снимки. Изменение критерия видно в `compare` и требует новой подачи. Повторное открытие сохраняет пользовательские записи |
| AC-23 | Ручной режим, инженер поднял M и указал основание | Аналитик уточняет затронутый BDD, РП запрашивает пояснение и принимает ответ | У трёх ролей одна переписка. До решения действителен прежний план. После решения сохранены новая редакция, разница, автор и основание |
| AC-24 | Владелец разрешил Чифу тип решения и пределы отклонения | Поступают предложения на границе допуска и за её пределами, затем одно предложение доставляется повторно | Первое применено один раз. Второе остаётся запросом к РП. Запись содержит значения до и после, версию правила и автора полномочий |
| AC-25 | Пока шло обсуждение, изменились границы этапа или входы оценки | Агент или человек пытается утвердить прежнее предложение | Показаны изменившиеся входы и действие «Пересчитать». Новое основание связывается с предыдущим обсуждением |
| AC-26 | Этап содержит оценённые и неоценённые фичи, есть журналы запусков и пропущенная проверка | Роли открывают свой экран и историю показателя | Видны состав этапа, охват, единицы, период и источники. Оценка, затраченное время и результаты проверок читаются раздельно. При отключённой анимации доступны те же значения и переходы |
| AC-27 | Инвариант зафиксирован в принятой редакции, в черновике предложено изменение, один тест пропущен | Пользователь открывает этап и проходит четыре вкладки, затем выбирает инвариант и повторно открывает обсуждение | Монитор команд показывает разные операции в одном контексте. На общей схеме видна цепочка «редакция → инвариант → задача → запуск теста», основания статусов и версия проверки. Прежняя редакция доступна. Пропуск и неизвестная связь обозначены явно |

### Нефункциональные требования

| ID | Категория / приоритет | Метрика или инвариант | Проверка |
| --- | --- | --- | --- |
| NFR-01 | Целостность / критический | Ноль непредусмотренных изменений основного проекта и контрактов в AC-03 и AC-08 | Нативные разрешения, снимки и сравнение хешей |
| NFR-02 | Восстановление / критический | Ноль повторных допусков без сверки при неопределённом состоянии | Потеря связи, остановка, восстановление и журнал точных ID |
| NFR-03 | Ограниченность / критический | Каждая попытка соблюдает сохранённые лимиты; передача роли не сбрасывает счётчики | Граничные тесты и живой сценарий достижения выбранного лимита |
| NFR-04 | Совместимость / критический | Прежние допустимые журналы и настройки читаются; неизвестный расход не превращается в ноль | Исторические фикстуры, миграционные проверки, сверка отчётов |
| NFR-05 | Сопровождаемость / важный | У каждой операции один владелец записи. Правила приёмки, бюджета попыток и PERT доступны независимо от представления | На ревью проследить одну операцию от входа до проверки. Найти владельца, зависимости и обработку отказа по схеме, именам и русским комментариям |
| NFR-06 | Документация / важный | У заявленной возможности есть проверка и актуальная инструкция | Трассировка FR → AC → задача → проверка и установка по руководству |
| NFR-07 | Прослеживаемость / критический | Для каждой отметки «Проверено» доступны редакция критерия, проверенная версия кода, условия и результат | Изменить порог в AC-12, открыть старый запуск из обоих экранов и проверить его привязку |
| NFR-08 | Воспроизводимость оценок / важный | Из сохранённых входов, единиц, версии метода и правил округления восстанавливается показанная оценка | Повторить AC-14 и AC-15, в том числе при отсутствии тарифа и вероятности |
| NFR-09 | Сохранность проектной документации / критический | При повторной установке, открытии другого проекта и сбое записи — ноль потерянных пользовательских правок и ноль записей в чужую базу | Два проекта с одноимённой фичей, перенос базы, параллельная ручная правка и повтор после сбоя |
| NFR-10 | Воспроизводимость решения | Одно предложение допустимо применить один раз к той редакции и набору входов, которые проверили. История фиксирует автора, роль, способ решения, правило, значения и основание | Две одновременные попытки, повторная доставка и перезапуск между решением и публикацией. Проверить историю и исходную оценку |

Задержку шлюза и допустимый объём истории нужно измерить на существующих
реализациях и задать границы до приёмки переноса. Они сейчас не измерены.
Лимиты попытки задаются действующей политикой; произвольные новые значения
из игрового примера не вводятся.

## 2. Plan: устройство и границы

### Кто принимает решения

Роли обозначают ответственность за результат. Один человек или агент может вести
несколько этапов. В записи решения остаются роль, автор, дата, редакция и основание.

| Роль | Что получает | Что передаёт дальше | За что отвечает |
| --- | --- | --- | --- |
| Руководитель проекта (РП) | Цель заказчика, ограничения по сроку и ресурсам, оценки инженеров | Границы поставки, приоритеты MoSCoW, смету, календарные допущения, реестр рисков | Сопоставляет пользу, срок и стоимость. Выносит изменение объёма и остаточный риск на решение владельца проекта |
| Системный аналитик | Согласованный объём, ограничения, примеры пользователя | Словарь, входы и выходы, инварианты, штатные и отказные сценарии BDD, паспорта NFR | Определяет наблюдаемое поведение и смысл данных. Вместе с инженером проверяет, что критерии можно измерить |
| Инженерный контур | Сценарии, ограничения и редакцию требований | Архитектурный контракт, техническую оценку, зависимости, код, результаты проверок и разбор реализации | Чиф отвечает за границы модулей, схему хранения, контракты, тесты и приёмку. Назначенный исполнитель реализует одно поручение, Bug Fixer исправляет отклонённую попытку в её границах |

Например, для паузы РП определяет, какую потерю работы может принять заказчик.
Аналитик задаёт, что увидит оператор при потере связи и что произойдёт с очередью.
Чиф проектирует состояния операции и способ подтвердить остановку, исполнитель
пишет назначенный участок кода. Рецензент может указать на пропущенную ветвь.
Решение о выполнении критерия опирается на код и проверку этой ветви.

Учебник v4 выделяет три решения человека. Для объёма и сметы сохраняются версия
предложения РП и допустимые расходы. Для архитектурного контракта — согласованные
интерфейсы, схема данных и редакция требований. Для релиза в продакшн — версия
сборки и результаты приёмки. Ранее данное согласование действует в записанных
границах. Выпуск рассматривается, когда входит в поручение пользователя.

### Переоценка этапа и обратная связь

**Реализация U-16.** В локальном дашборде доступна страница `/stage`.
Одна база проекта хранит обсуждения, редакции, трассировки и решения РП.
Доступны четыре вкладки, флажки поручений, известный труд в чел·ч и график
связанных запусков. Для переоценки применяются ручное решение и полномочия
на изменение трудозатрат. В U-10 управленческая вкладка принимает календарь,
состав команд, ставки и отдельные записи учёта. Индивидуальная аутентификация
сотрудников не входит в действующий режим локального оператора.

На этапе `project-docs` в браузере проверены переключение команд, повторное
обсуждение и переход из FR-23 к именованному тесту. После записи результата
в BDD прежнее предложение по оценке показало изменённый документ. Новое
предложение связано с прежним и ожидает решения РП. Принятая редакция
инварианта с пропущенным тестом проверена в отдельной тестовой базе.

**С обсуждением.** При следующей оценке инженер сохраняет новые O/M/P и
указывает, что изменилось. Аналитик сравнивает границы, BDD и NFR двух редакций.
РП видит старый и предложенный труд, доступную ёмкость, срок, стоимость и
риски в тех единицах, для которых есть основания. РП может принять, отклонить
с причиной или адресовать уточнение конкретной роли. У вопроса видны автор,
адресат, что требуется для ответа, блокирует ли он решение, ответы и ссылка на
источник. Каждая роль видит ожидаемое от неё действие. Пока идёт переписка,
утверждённая оценка продолжает действовать.

**Автоматически в согласованных пределах.** Владелец указывает для проекта
или этапа типы разрешённых решений, пределы, единицы и срок действия правила.
Для ручного режима каждое предложение ждёт решения. Для автоматического
нужны текущая редакция, полные входы для конкретного решения, выполненные
условия правила и ответы на блокирующие вопросы. При отсутствии правила,
конфликте резервов, выходе за пределы или изменении объёма вне полномочий
Чиф создаёт запрос к РП с причиной. Отличайте фоновый пересчёт прогноза
от изменения утверждённого плана. Согласование в этом процессе не публикует релиз.

**Навигация командного монитора.** Пользователь выбирает этап один раз. У него
четыре вкладки — «Управление», «Анализ», «Инженеры» и «Совместная работа».
В первых трёх фильтруются действия команды. Четвёртая показывает передачу
работ между ролями и одну ветку обсуждения для каждой темы. Из неё можно
вернуться к роли и исходному документу с сохранением выбранного пункта.
Вопрос можно открыть повторно после ответа, указав причину и редакцию.

На общей схеме узлами служат части спецификации, инварианты, задачи этапа
и результаты конкретных запусков тестов. Выбор узла показывает владельца,
версию, статус, входящие и исходящие связи. У замороженной части видны ID
принятой редакции и основание фиксации. Предложенную правку показывать рядом,
со ссылкой на отличие. Тест привязывается к проверенной версии правила.
Пока связь не установлена, схема показывает «Проверка не связана».

**Три рабочих места.** В шапке каждого — один этап, его редакция, текущие пункты
и время обновления. У РП первым идёт список решений с отклонениями и ресурсами.
У аналитика — вопросы, спорные требования и изменившиеся критерии. У инженеров —
изменившиеся работы, зависимости, O/M/P, попытки и результаты проверок.
Роль выбирает нужное представление. Полномочия на решение проверяет операция
сохранения по отдельному правилу. Представления читают единый журнал обсуждения.

**Динамика.** Лента отмечает, когда появился вопрос, кто ответил, какую
редакцию оценили и когда приняли решение. График плана, прогноза и факта
опирается на датированные снимки и записи фактического труда. Если есть
только время выполнения задачи агентом, оно показывается своей серией.
Для прогресса показывать принятые пункты и весь согласованный состав
на соответствующую дату. При смене состава отмечать событие на графике.
Для ресурсов показывать зарезервированные и доступные чел·ч по ролям за период.
Для проверок — прошедшие, упавшие и пропущенные. На точке доступны редакция,
источник и время наблюдения. Пробел в истории виден на графике. Анимируется
переход при поступлении нового события, с учётом настройки уменьшенного движения.

### Что видит пользователь

**«Рабочее место»** открывается при входе в проект. Единица работы — возможность
продукта, например «Приостановить задачу». Навигатор показывает возможности;
выбранная запись открывается с целью, редакцией и ответственным. Если записей
ещё нет, доступно создание первой возможности из описания пользователя.

| Раздел | Что можно сделать | Как понять результат |
| --- | --- | --- |
| Требования | Записать цель, границы, приоритет и инварианты | По ID видны связанные сценарии, паспорт качества и открытые решения |
| Сценарии BDD | Разобрать с пользователем пример, записать исходные условия, действие и результат | Видны связанный тест, его версия и исход. Для ручного сценария сохраняются наблюдение и условия |
| Качество (NFR) | Задать метрику или инвариант, порог, среду, нагрузку, выборку и способ проверки | Рядом с порогом видны фактическое значение, дата и редакция. При отсутствии замера видно, чего именно не хватает |
| Оценка работы | Разложить работы, указать O/M/P и ресурсы, сопоставить план с фактом | От результата можно перейти к исходным числам и допущениям. [Методика трудозатрат](EFFORT_ESTIMATION.ru.md) |
| Риски | Связать событие с задачей, оценкой, владельцем и мерой | Видны основание вероятности, учёт в резерве и срок следующего решения. [Методика рисков](RISK_ASSESSMENT.ru.md) |

Из каждого раздела доступны поручение, попытка и свидетельство проверки, если
они существуют. Значения спецификации хранятся в читаемых версионируемых
документах проекта. Рабочее место редактирует этот же источник. При конфликте
версий оператор видит обе редакции до приёмки. В Obsidian рабочие документы хранятся
в `Документы/<ID>/` в формате Markdown. Обзор и карточка ссылаются на одни файлы;
их текст при постановке хранится в заявке и затем в архиве принятой редакции.
Инженер вводит O/M/P, аналитик ведёт критерии, РП определяет способ учёта
каждого риска. Сохранение любой исходной таблицы обновляет сводку в рабочем
месте. Одна строка риска относится к одной или нескольким работам. Решение
«отдельно» добавляет согласованные чел·ч один раз. При противоречии с риском,
включённым в O/M/P, вместо числа показаны причина и ID. Для неполных данных
виден охват. Для проверки навигации применяется AC-22.

**«Три контура»** открывается для обзора проекта. РП видит границы, ёмкость,
сроки, смету и риски. Аналитик видит открытые вопросы, изменившиеся контракты
и критерии без проверки. Инженер видит задачи, зависимости, попытки, тесты
и неподтверждённые остановки. Нажатие на отклонение открывает исходную запись
в «Рабочем месте». Расчёты и статусы для двух экранов поступают из одних данных.

В проектной базе реализован путь по FR-15 и AC-13. Задачу назначают флажком
и меткой роли в документе фичи. В обзоре сохраняются её ID, этап, последняя
сохранённая редакция и путь к этому документу. Показаны открытые поручения,
суммы и риски по работам, изменённые условия, явно отсутствующие результаты
BDD/NFR и открытые заявки со связанными журналами. Источник выполнения —
флажок в исходном документе. Сведения о приёмке берутся из истории редакций.

14.11.2026 путь AC-13 проверен в Obsidian на базе проекта Чифа. Из обзора РП
открыл риски `effort-risk`, аналитик — BDD `role-overview`, инженер — NFR
`role-overview`. После закрытия одного из двух инженерных поручений в NFR
счётчик инженеров показал 1. Остальные два контура сохранили свои поручения.
Из заметки «Монитор Чифа» можно перейти к той же записи и роли в браузере.
Вкладка «Управление» сводит сроки, ёмкость и реестр рисков выбранного этапа.

**«Документация проекта»** — точка входа со стороны базы знаний. На ней видны
назначение, этапы, возможности, ответственные, решения и последние результаты.
Карточка этапа показывает его фичи и зависимости. Действие «Доработать этап»
открывает его состав, срок, оценку и риски. Действие «Доработать фичу» открывает
её требования в «Рабочем месте». В обоих случаях кит получает ID проекта и этапа,
тип и ID выбранной записи и номер редакции, с которой начал пользователь.
Обратное действие «Открыть документацию» возвращает к этой же записи.
Учебник хранится отдельно от рабочих карточек.

База может находиться вне Git-репозитория. Для каждого документа хранится
место, где его редактируют. Например, спецификация контракта в Git может быть
связана с карточкой фичи в Obsidian. При их изменении Чиф связывает редакции
и показывает расхождение, если правки пересеклись. Журнал выполнения остаётся
источником факта о попытке и её проверках. Карточка ссылается на этот результат.
На другом компьютере привязку восстанавливают по ID проекта и выбранному пути.

**Пример паспорта NFR для FR-07.** Для отклика интерфейса отсчёт идёт от нажатия
«Приостановить» до показа «Пауза запрошена». Для времени остановки отсчёт идёт
от регистрации операции до подтверждения остановки семейства. Это два разных
замера. Инженер фиксирует версию среды, число исполнителей, нагрузку, выборку и
процентиль. Порог согласуется по исходным замерам. Сохранность очереди при обычной
паузе проверяется отдельным сценарием AC-06. Обе задержки пока не измерены.

| Установка Obsidian | Обнаружить приложение, подобрать официальный пакет, установить, проверить запуск и подключить базу | Возможности ОС, сеть и ответ установщика. При системном запросе прав оператор видит, для какого шага они нужны |

Доставка предусматривает Windows и поддерживаемые комплектом дистрибутивы Linux.
Кит получает официальный пакет во время настройки. Имеющаяся совместимая
установка используется повторно. Подтверждение ОС, отказ от установки,
недоступная сеть и неподдерживаемая платформа имеют отдельные исходы.
Проверка U-15 включает запуск на чистой системе и открытие правильной заметки;
наличие файла приложения само по себе недостаточно. [Установка Obsidian](https://obsidian.md/help/install) · [Открытие заметок](https://obsidian.md/help/uri).

Это границы ответственности проектируемой системы. Разметка экранов, CLI агента и
формат файла могут меняться независимо от формулы PERT или правил приёмки. Где
эти границы уже проходят в текущем коде, показано в [путеводителе разработчика](DEVELOPER_GUIDE.ru.md).

Выбор шлюза остаётся одной явной точкой. Реализация этой границы уже есть
в Pi-репозитории; сначала сопоставляются версии и утечки формата OpenCode.
Общие интерфейсы вводятся под операции, нужные контроллеру и управлению.

Состояние задачи и состояние процесса различаются. Отправка задания не
доказывает завершение; запрос abort не доказывает остановку; готовый код не
означает приёмку. Неопределённое состояние блокирует замену исполнителя до
сверки. Схемы событий и сигнатуры фиксируются в U-02 по реальным реализациям.

OpenCode-проект без выбора новой среды сохраняет прежнее поведение. Ключи
и локальные настройки не входят в поставку. Чтение истории, управление уже
открытым разговором и запуск управляемой сессии проверяются раздельно.
Интерфейсы Codex и Claude Code ещё требуют предметной проверки: наличие
SKILL.md не подтверждает управление выполнением.

## 4. Implement & Validate: определение готовности

Поручение принимается существующим доказательным протоколом, этап — по своим
FR/AC и NFR. Меняются вместе спецификация, задача, проверки и затронутые
инструкции, руководства и оба README. Понятные обязанности, имена и комментарии,
явные границы состояния и отсутствие расходящихся общих правил входят в ревью.
Наличие паттерна или большого числа классов не является критерием качества.

Приёмка среды требует реального запуска по её инструкции. Тесты ядра не
засчитываются как живой запуск агентов. Пропуски, неизвестный расход и
невыполненные проверки отражаются явно. Ход работ хранится в разрешённом
currentsteps.md; фактические результаты — в журнале задачи.
